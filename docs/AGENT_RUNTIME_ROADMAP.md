# AgentScratch：真实小模型 Agent Runtime 路线图

> 更新日期：2026-09-08
> 目标：以不失真的 Agent 运行逻辑，帮助初学者理解上下文、工具、Observation、ReAct 与 Harness；同一内核后续复用于 Agent 战斗沙盒，最后才面向端侧部署优化。

## 一、总原则

AgentScratch 的教学演示必须遵循真实工具调用协议，而不是用规则 Mock 冒充模型决策：

```text
LLM 根据本轮 Context 提出 tool_calls 或最终文本
  → Harness 校验、调度并执行
  → Harness 写入带 call_id 的 Observation
  → Context Builder 组装下一轮请求
  → LLM 继续决策
```

- **LLM** 负责语义理解、目标权衡、选择候选工具与填写参数。
- **Harness** 负责 Schema、权限、资源隔离、依赖、并发、重试、循环上限、状态持久化和完成条件验证。
- LLM 可以建议并行调用；Harness 始终拥有是否允许并行的最终裁决权。
- Mock Brain 仅用于自动化测试或标注为“确定性演示”的案例，不能替代默认真实 LLM 主线。

P0 已移除曾用于兼容 `qwen-tiny` 案例的“异常后自动收束最终答案”规则。真实多工具任务不能因为已有一个 Observation 就提前结束；模型必须明确产生下一步 `tool_calls` 或 `final_answer`，否则运行以可回放错误结束。

## 二、路线总览

| 阶段 | 目标 | 退出标准 |
|---|---|---|
| P0 | 真实工具调用内核与上下文重构 | 原生 tool_calls、Observation、状态和回放一致 |
| P1 | 打磨基础工具与多工具教学案例 | 两文件读取、并行、依赖调用可真实运行 |
| P2 | 小模型档案、评测与专项微调闭环 | 0.5B / 1.5B / 3B 可比较、可复现实验 |
| P3 | Agent 战斗沙盒与战斗技能 | 同一 Runtime 驱动可回放的半回合对战 |
| P4 | 端侧低算力部署 | 在目标设备上测得可接受延迟与成功率 |

端侧部署放在最后：先确保协议和教学逻辑正确，再为设备限制做裁剪和性能优化。

## 三、P0：真实工具调用内核与上下文重构

### 目标

将目前的兼容 `json_action` 教学 DSL 降为可选适配层，Runtime 的规范表示统一为：

```text
system / user / assistant(tool_calls) / tool(tool_call_id)
                     + request.tools
```

### 实施项

1. **规范化事件与状态**
   - 每个调用有稳定的 `call_id`、工具名、参数、开始/结束时间、状态和错误。
   - Observation 同时进入不可变事件日志与结构化 Run State，例如 `observations[call_id]`。
   - Run State 是恢复、依赖判断、UI 展示的权威来源；它不是模型记忆的替代品。

2. **Context Builder**
   - 每轮由状态构建模型真实收到的 `messages` 与顶层 `tools`。
   - 保留必要的 assistant tool_calls 和相应 tool Observation。
   - 追加紧凑状态栏：当前步骤、已完成/等待调用、资源、预算、失败次数和未满足依赖。
   - 长文件和冗长结果采用摘要、字段提取或按需检索，不能无上限堆入 prompt。

3. **调用验证与调度器**
   - 验证工具名、JSON Schema、资源引用、权限、风险、用户确认和调用上限。
   - 模型可在一次响应中返回多个 tool_calls。
   - 只有所有调用均为只读、`parallel_safe`、无共享资源冲突、且参数不依赖未完成 Observation 时才并行。
   - 参数可显式引用 Observation，例如 `${obs.read_A.values[0]}`；引用未完成结果的调用必须等待。
   - 重复调用、无进展、超时和最大轮数应产生可解释的错误/暂停，不得擅自伪造最终答案。

4. **教学画布与回放**
   - 将 assistant tool_calls、各个 Observation、并发组、等待依赖、状态栏投影清楚展示。
   - Context 卡片展示“本轮实际发送给模型的内容”与“运行时完整状态”的区别。
   - 继续保留 ReAct 动画：Context → LLM → tool_calls → Tool Runtime → Observation → Context。

### 验收

- 一个真实模型调用工具后，下一轮请求包含原 assistant tool_calls 与匹配的 `tool_call_id` Observation。
- 暂停、续跑、SSE、SQLite 恢复和回放不会丢失调用关联。
- 将当前单计算器 `tiny_llm` 案例改为真实协议；不能靠通用自动收束掩盖模型错误。

## 四、P1：基础工具与多工具教学案例

### 工具注册表第一批

| 工具 | 类别 | 关键限制 |
|---|---|---|
| `read_document` | 感知 | 只读取用户加入工作区的 `file_id`；类型/大小限制 |
| `extract_numbers` | 感知/转换 | 输入为文本或已读取文档 Observation；返回带来源的结构化数值 |
| `calculator` | 纯计算 | 无副作用；参数与结果可验证 |
| `search_notes` | 感知 | 仅查询本地教学语料/工作区索引 |
| `code_interpreter`（后续可选） | 通用执行 | 隔离沙盒、CPU/时间/网络限制 |
| `ask_user` | 用户沟通 | 明确暂停与恢复契约 |

文件是 **资源**，工具是 **操作资源的能力**。模型永远不能直接传任意本机路径；只能使用用户显式提供的资源 ID 和 Harness 的授权范围。

### 教学案例

1. 无工具的一问一答。
2. 单工具计算：调用 calculator 后给出答案。
3. 并行读取：同轮 `read_document(A)` 与 `read_document(B)`。
4. 依赖链：读取 A/B → 提取数值 → calculator → 最终回答。
5. 失败恢复：读取权限不足 / 参数无效 → Observation → 追问或合法替代动作。
6. 高风险确认：写入或敏感工具在执行前等待用户确认。

### 工具按需暴露

工具库增长后不应每轮全量注入。采用三层机制：

1. **画布授权**：Context 的工具定义模块与 Agent 工具勾选项构成硬白名单。
2. **Harness 推荐**：根据用户任务、已提供资源类型、当前状态和工作流阶段检索 Top-K 工具。
3. **主动发现（后续）**：模型只能请求检索工具能力；Harness 返回受审核的候选 Schema，再临时注入。

推荐工具不是授权；最终可调用集合始终是“用户/画布授权 ∩ Harness 策略允许”的结果。

### 验收

当前已提供受限的 `file-a` / `file-b` 教学工作区与确定性演示轨迹，可展示两个读取调用并行、两个 Observation 写回、数值提取与 calculator 的依赖步骤、最终回答。下一步将接入用户提供的资源与真实小模型评测；所有工具调用均必须可回放和复现。

## 五、P2：模型档案、评测与专项微调

### 模型档案

保留 0.5B、1.5B、3B 三档，不将模型大小简单视为高低版本：

| 档位 | 主要教学意义 |
|---|---|
| 0.5B | 极低算力、固定工具、短链路与强 Harness |
| 1.5B | 轻量实用 Agent、多工具短到中链路 |
| 3B | 更复杂规划、更多 Observation 和较长任务 |

每个档案记录模型、量化、上下文上限、提示 token、生成 token、工具解析率、调用成功率、轮数、实际延迟与逻辑计算成本。

### 先评测，后训练

建立隔离的可重放评测集，指标包括：

- JSON / native tool_calls 解析成功率；
- 工具选择、参数、权限处理正确率；
- 并行调用精确率/召回率；
- 依赖顺序正确率；
- 最终答案正确率、平均 ReAct 轮数、重复调用率；
- 端到端延迟与每轮上下文成本。

### 专项 SFT / LoRA

只针对稳定、有限、版本化的教学工具集训练。样本是经过可执行验证的完整轨迹：

```text
任务 + 已授权工具 + 初始资源
→ assistant.tool_calls
→ tool Observations
→ 下一轮 tool_calls 或最终回答
```

- 用人工种子 + 强开源教师模型生成候选 + Harness 回放验证/拒绝采样构造数据。
- 只对模型生成的 assistant 文本和工具调用参数计算训练损失；Observation 是环境反馈，不训练模型背诵。
- 覆盖并行、依赖、权限拒绝、参数修复、追问、停止和反例。
- 先以 SFT 固化协议；只有模型已有非零成功率、环境和奖励可靠时才研究 RL。

### 验收

微调前后在未见文件、未见数值和未见工具组合上比较。不得只报告训练集成功率；应说明成功率、延迟、上下文成本与失败类别变化。

### P2-A：已落地的训练准备与离线评测底座

当前先固定最稳定的 `JSON Action` 协议，避免把尚未经过 tool-use 微调的模型在 Native Tool Calling 上的格式失败，混入第一轮专项训练信号。

- 轨迹级切分为训练、验证和保留评测集；同一条轨迹绝不会同时出现在训练和评测中。
- 训练目标刻意不包含运行期 `call_id`：这些 ID 由 Harness 为每次真实执行生成，模型只学习选择工具和填写参数。

这不是“模型已经微调完成”的宣称。下一小步是用同一保留集跑出当前 0.5B / 1.5B / 3B 基线，再以经 Harness 回放验证的真实失败修复轨迹扩展数据，最后才启动 LoRA 实验。

## 六、P3：Agent 战斗沙盒

### 定位

战斗沙盒不是脚本 AI 游戏，而是 P0/P1 同一 Agent Runtime 的第二个环境：把工具替换为战斗技能，把 Observation 替换为战场状态。

### 核心机制

- **技能即工具**：`scan_enemy`、`attack`、`defend`、`charge_weapon`、`hack_shield` 等均有 Schema、冷却、资源、风险和依赖。
- **角色配置**：玩家选择已授权技能、模型档位、上下文/记忆预算、思考预算和专项 LoRA 档案。
- **真实 Observation**：每次动作结果、护盾、伤害、资源、冷却等通过 tool Observation 写入下一轮 Context。
- **半回合制**：双方从同一战场快照并发推理；完成并校验通过的一方先执行。后完成的计划若因状态变化失效，收到失败 Observation 后重新规划。
- **不展示私有 CoT**：展示计划摘要、tool_calls、Observation、状态栏和延迟，不要求暴露隐藏推理链。

### 公平性

同时记录：

1. 实际墙钟延迟，用于展示不同模型/硬件的真实速度；
2. 逻辑计算成本，由 prompt token、生成 token、模型基准吞吐与工具耗时计算，用于跨设备对战平衡。

玩家可体会的取舍：更长记忆和更高思考预算可能提升规划质量，但会增加计算成本和出招延迟；它们不保证必胜。

### 验收

- 对局可完全回放，并能逐步展示每次模型决策、技能调用和状态变化。
- 游戏规则由 Harness 强制：模型不能绕过冷却、资源、授权、依赖或回合限制。
- 战斗技能训练数据和教学工具训练数据采用同一轨迹、验证、评测基础设施。

## 七、P4：端侧低算力部署（最后阶段）

在 Runtime、工具协议和评测稳定之后，再面向嵌入式/终端设备做优化：

- 选择目标硬件与功耗/内存预算；
- 评估 GGUF 量化、上下文窗口、KV Cache、线程与推理后端；
- 采用工具按需加载、状态栏、Observation 摘要和小上下文投影降低 prefill 成本；
- 使用 P2 基准在真实设备上测吞吐、首 token 延迟、工具调用成功率与任务成功率；
- 保持与课堂/战斗环境相同的 Runtime 协议，避免为端侧另写一套失真的规则引擎。

## 八、当前下一步

从 P0 开始，先完成标准工具调用与状态/上下文重构的设计评审，再实现 `read_document`、`extract_numbers`、`calculator` 的可回放多工具案例。P3 和 P4 不提前实现，以免战斗规则或设备限制反向污染教学内核。
